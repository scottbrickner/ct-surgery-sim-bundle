# CLAUDE.md — CT Surgery Sim Bundle

Training simulation only, not for clinical use — enforce this framing in any UI copy/disclaimers.

**Read `docs/BUILD_PROMPT.md` before doing anything else in this repo.** It is the governing spec: what to reuse, the resolved architecture decisions, the transcribed flagship scenario, and the phased plan. This file only adds working conventions for whoever (human or Claude) picks up the next phase.

## Where things stand

**Phase 0** (consolidation) is done: the three device prototypes and the pacemaker's relay code are copied in **unmodified** — see README.md for the exact file map.

**Phase 1** (shared physiology engine + unified scenario schema) is done: `engine/physiology.js` + `engine/scenarioRunner.js` (35 passing `node --test` tests total, zero dependencies) and `scenarios/ct-surgery-flagship.json` (the transcribed 3-part case, validated by its own end-to-end test). Read `scenarios/schema.md` before authoring or editing scenario data.

**Phase 2** (wire IntelliVue + HemoSphere Alta to the engine) is done. Both device files now `<script type="module">` import `engine/physiology.js` + `engine/scenarioRunner.js` directly and fetch `scenarios/ct-surgery-flagship.json` at load time, driving a new "Shared Flagship Scenario" facilitator-panel section.

**Phase 3** (generalize pop-out + BroadcastChannel/relay sync) is done for the two monitors. `sync/deviceSync.js` (BroadcastChannel + localStorage mirror for same-machine, opt-in WebSocket relay for cross-device, 9 passing `node --test` tests on its pure logic) is wired into both device files: each device pushes `{partIndex, stepIndex, state}` on a 140ms interval and applies whatever a peer last pushed, so driving the scenario on either one updates the other live. Both also gained a generalized `?role=learner` pop-out (hides all facilitator chrome via `body.learner` CSS, still syncs) and a "Cross-Device Sync" facilitator-panel section (relay URL input, Connect, Copy Learner Link, Open Learner Display).

**The pacemaker is still NOT wired into any of this, deliberately.** It keeps its own separate, mature BroadcastChannel(`'sim5392'`)/relay sync from before this repo existed — untouched, unrelated to `sync/deviceSync.js`. Don't try to merge the two sync systems or make the pacemaker participate in the monitors' session in this phase. Actually cross-wiring pacer capture state into the shared physiology engine (so losing capture there visibly changes IntelliVue's rhythm) is explicitly **Phase 5** (BUILD_PROMPT.md §9), not Phase 3 — Phase 3's scope was strictly the monitor-to-monitor sync bus and the pop-out pattern, both done. Don't assume any pacer<->monitor interaction exists until Phase 5 builds it.

**Phase 4** (unify the facilitator UI) is done, but NOT by stripping the per-device panels — see the "important product decision" note below before changing this. `facilitator/console.html` is a new standalone page (imports `engine/`, `scenarios/`, `sync/` directly - zero new modules, zero duplicated logic) meant to run on the instructor's own laptop: the same Next/Prev/Reset/Part-jump/coach-text UI as the devices, a full override-slider set (the UNION of what IntelliVue's and HemoSphere's panels each separately exposed, plus gaps neither covered alone - notably `bp.map` as a direct override, which previously only existed on HemoSphere's panel), a rhythm dropdown + pacer-capture toggle + event-flag toggles (all via `applyFacilitatorOverride`, not ramp-restricted), a live compact readout grid, and per-device `?role=learner` link generation (with relay/code passthrough) so a monitor opened from a generated link needs zero manual config to join the console's session.

**Important product decision, don't silently reverse it**: IntelliVue's and HemoSphere Alta's own local "Shared Flagship Scenario" + override-slider sections were NOT removed when the console was built. BUILD_PROMPT.md's Phase 4 wording ("unify... into one control surface") could be read as replacing them, but doing so would break solo single-device testing/demoing, which was a working, verified feature since Phase 2 - and nothing about the sync architecture requires a single driver (any device, now including the console, can drive the scenario; the others just follow). Each device panel got a one-line pointer to the console instead. If a future request explicitly asks to strip the device panels down to local-only controls, that's a reasonable, different call - just make sure it's an explicit ask, not an assumption.

**Phase 5** (pacer<->ECG/hemo feedback loop + Training/Validation mode across all three devices + optional iPad relay peer) is done. The pacemaker now joins `sync/deviceSync.js`'s bus too, via a small addition inside its existing IIFE (`window.__pacerBridge`, exposing a `getState()`/`getNotifyMode()`/`setNotifyMode()` surface) plus a brand-new, separate `<script type="module">` tag appended after the original script closes. A few things worth knowing before extending the engine or its device wiring further:
- `engine/scenarioRunner.js`'s navigation is **replay-based, not incremental**: `prev()`/`jumpToPart()`/`reset()` all recompute state from a part's `initialState` by replaying its steps (`computeStateAt`), rather than trying to invert a ramp or undo a patch. `next()` relies on the same function for whatever step it's leaving, which is *why* it can cleanly force-settle an in-flight ramp to its target before advancing — there's no separate "settle" code path to keep in sync if you add a new step type.
- Each scenario **part** has its own independent `initialState` — parts do NOT carry the previous part's ending state forward. This matches the source case study, which gives each part (SIM 1 / Scenario 2 / Scenario 3) its own fresh "Start of scenario" vitals after an off-screen time skip. If you add a 4th part, give it a complete `initialState`, don't assume it inherits Part 3's ending values.
- `bp.map` is always an independently authored field, never derived from `sbp`/`dbp` via the textbook formula — see `engine/physiology.js`'s comment and `scenarios/schema.md` for why (the source case's charted MAPs don't match the formula).
- The Part 2 `arrest` step sets `pacer.captured: false` alongside `rhythm: 'PEA'` — that's the pacer<->ECG feedback loop from BUILD_PROMPT.md §3.1 actually being exercised. If you add more arrest/capture-loss moments, remember `getEffectiveRhythm()` only reveals the intrinsic rhythm when `captured` is explicitly false, OR when demand-inhibited (see next bullet) — setting `rhythm` alone does nothing while the pacer is actively pacing.
- **`getEffectiveHR(state)` mirrors `getEffectiveRhythm()` for the HR number**, added after live class testing surfaced a real gap: the rhythm label correctly showed "Paced (VVI)" while captured, but the HR *number* on IntelliVue and HemoSphere Alta kept showing the intrinsic `state.hr` instead of the pacer's actual captured rate. Both device files now compute `getEffectiveHR(es)` inside `applyEngineValuesLight` and assign it to the same local field that already drove both the numeric tile AND the waveform beat-timing math (`state.hr` on IntelliVue, `drv.pr` on HemoSphere Alta) — one assignment fixes both. The console's readout does the same for its `hr` row.
- **Demand-inhibition is modeled**, via a shared private `isPacing(state)` helper both `getEffectiveRhythm()` and `getEffectiveHR()` call: a demand pacer only actually fires when the intrinsic rate falls below its programmed rate (`state.pacer.rate >= state.hr`) — if the intrinsic rate is faster, the pacer senses those native beats and sits inhibited, so the intrinsic rhythm/rate shows through even with `captured: true`. `captured` (hardware capture: would a delivered spike depolarize the myocardium, independent of whether the pacer is being asked to fire at all) and demand-inhibition (rate-based: is the pacer even firing) are two independent gates - a paced display requires both. This was a known, explicitly-documented limitation of the original `getEffectiveHR` (deferred to avoid touching "highest-risk clinical timing logic" before the simpler HR-sync fix shipped and got live-tested) that a subsequent round of class testing asked for directly. If you add more captured-rate scenario data, `Part 3-ecmo-cannulation`'s baseline sets `pacer.captured: false` even though `isPacing()` would already resolve to demand-inhibited via the rate comparison alone (`hr: 140` vs `pacer.rate: 90`) - that's now redundant-but-harmless, left as-is rather than silently reinterpreted.
- **Per-device wiring pattern** (both files follow this identically - copy it for the pacemaker in Phase 3, don't invent a third variant): convert the file's single big `<script>` to `type="module"` (safe only because neither file uses inline `onclick=` attributes - everything's wired via `addEventListener`, confirmed before doing this); import the engine at the top; append an additive block at the bottom that (a) fetches the flagship JSON and calls `createRunner`, (b) exposes a light per-tick apply function used ONLY during a live ramp (numeric fields only, no canvas/layout calls) versus a full-apply function used on discrete Next/Prev/Reset/jump (which also refreshes tile visibility and calls the device's own `layout()`), (c) wires the vital-sign sliders to ALSO call `applyFacilitatorOverride` in addition to their existing local-state binding, and (d) exposes `window.ctSharedEngine = {getRunner, getState, getDeviceState, tickNow}` - read-only introspection used by verification tooling today and the attachment point Phase 3's sync layer should read from.
- **Decompensation auto-advance ("if nobody addresses it, the patient arrests on their own")**, added after a facilitator asked whether the SME actually has to click through every scripted beat by hand or whether the sim can play out unaddressed vitals into a bad outcome on a timer. A `ramp` step can carry an optional `autoAdvanceAfterMinutes` (see `scenarios/schema.md`) - `engine/scenarioRunner.js`'s `next()` schedules `pendingAutoAdvance:{fireAtMs}` the instant the ramp starts (everything needed - start time, ramp duration, grace period - is already known then, so this is NOT discovered reactively when the ramp completes). Every tick loop (console + both devices) also calls the new `checkAutoAdvance(runner, nowMs)` alongside the existing `tick()`; once the deadline passes with no facilitator navigation, it fires `next()` itself - same effect as a manual Next click, including the same full re-render (part title/coach text/tile refresh), not just a light numeric update. `getRampProgress()`/`getAutoAdvanceCountdown()` are read-only views the UI polls every frame to render a live decompensation timer (progress bar while the ramp itself is running, then a countdown once it settles and the grace period starts) - see the `#decompTimer`/`#fs_decomp` element and `renderDecompTimer()` in each file. `cancelAutoAdvance()` lets the facilitator explicitly hold the current state open past the deadline (a visible "Hold Here — Cancel Auto-Advance" button); manually navigating via `next`/`prev`/`jumpToPart` cancels it too, as a side effect of moving on. The flagship scenario's `tamponade-onset` ramp now sets `autoAdvanceAfterMinutes: 3` (5-min ramp + 3-min grace = minute 8, matching the source case's "At 8 min, patient goes into cardiac arrest," which `arrest`'s pre-existing `atMinute: 8` already documented). **This is still a fixed, linear script, not reactive branching**: the auto-fired step is always whatever comes next in the JSON (typically the authored `arrest` event) - nothing checks what the learner actually did (meds started, pacer captured, etc.) and there is no alternate "good outcome" path. **Cross-device note**: `pendingAutoAdvance` (like `activeRamp`) is deliberately NOT included in `sync/deviceSync.js`'s snapshot payload, for the same reason `activeRamp` isn't (see the sync-payload bullet above) - only the device that actually called `next()` locally (typically whichever one the facilitator is driving from) ticks its own countdown and can fire the auto-advance; other devices/consoles just receive the resulting state change once it happens, same as they already do for ramp ticking.
- **Custom Decline (facilitator-timed, SME-configured)** - the follow-up to the bullet above. Only Part 2's `tamponade-onset` has a scripted `ramp` step in the flagship JSON; Part 1 has NO steps at all ("no engine transition, assessment/orientation only" per the source case) and Part 3 has no `ramp` step either (static post-sternotomy baseline + discussion prompts, no further scripted decline in the source). Rather than fabricate new clinical vitals trajectories for those parts on my own judgment, this instead generalizes the MECHANISM: `startFacilitatorRamp(runner, {target, durationMinutes, autoAdvanceAfterMinutes, outcomePatch, label}, nowMs)` lets the SME configure and start a decline live, with their own target vitals/duration/grace-period/outcome, from ANY point in ANY part - entirely independent of `partIndex`/`stepIndex` (same "independent of the scripted timeline" spirit as `applyFacilitatorOverride`, just for a ramp+auto-advance instead of an instant patch). `checkAutoAdvance()` now branches on `pendingAutoAdvance.kind`: `'scripted'` (set by `next()` from a JSON-authored ramp step, as before - fires by calling `next()` again) or `'custom'` (set by `startFacilitatorRamp()` - fires by `applyInstant`-ing an arbitrary `outcomePatch` onto `state`, WITHOUT touching `partIndex`/`stepIndex`, since a facilitator-timed decline isn't tied to any scripted step). `getAutoAdvanceCountdown()` now also returns a `label` (custom declines only, null for scripted ones) so the UI can show e.g. "Auto-advancing to cardiac arrest if unaddressed in 2:14" instead of a generic message. **The UI (`facilitator/console.html` only, not yet the two device panels' own local flagship sections)** exposes this as a "Custom Decline" card: 6 target sliders (HR/BP sys/BP dia/MAP/CVP/SpO₂ - intentionally a subset of the full Override Parameters sliders, kept compact) that describe where the decline ENDS UP (deliberately NOT wired through the instant-apply `OVERRIDE_MAP`/`applyFacilitatorOverride` pattern the Override Parameters sliders use - dragging one must only update its own displayed number, never touch live state, since it's a future ramp target, not an immediate change), a duration + grace-period number input, and an outcome dropdown of mechanically-defined preset patches (not fabricated clinical content) - "Cardiac Arrest (PEA)" reuses the exact same patch shape as the flagship's own scripted `arrest` event, "Loss of Pacer Capture" just flips `pacer.captured`, and "Hold" runs a decline-only ramp with no auto-fire. The existing `#decompTimer`/`renderDecompTimer()` from the bullet above already displays a custom decline's progress/countdown/cancel button correctly with ZERO changes, since it was already written generically against `runner.activeRamp`/`pendingAutoAdvance` rather than assuming a scripted source - it's now mirrored into a second element (`#cdTimer`, next to the Custom Decline card) purely so the SME doesn't have to scroll back up to the Flagship Scenario card to see the countdown they just started further down the page. If you extend this to the two device panels' own local sections later, copy this exact pattern (separate un-wired target sliders + `startFacilitatorRamp` + the existing generic timer render function) rather than inventing a variant.
- **V-Fib and V-Tach are real, distinct rhythms now** - `IntelliVue_Sim_Monitor.html`'s own native rhythm engine (Phase 0, pre-existing/unmodified) already had full `vfib`/`vtach` support - actual fibrillatory/fast-monomorphic ECG waveform morphology, `"*** VENT FIB"`/`"*** VENT TACH"` alarm banners, suppressed HR display, near-flatline ART - it just wasn't reachable through the shared flagship engine's rhythm vocabulary. `RHYTHM_MAP` now maps `"Ventricular Fibrillation"`→`vfib` and `"Ventricular Tachycardia"`→`vtach` (unlike `PEA`, which still only borrows `sinus_tach`'s morphology - there was no pre-existing native PEA waveform to map to). Both are now selectable in the console's "Intrinsic rhythm" dropdown (`ov_rhythm`) directly, AND as two more Custom Decline outcome presets (`vfib`/`vtach` in `CD_OUTCOME_PRESETS`) alongside the existing PEA arrest - same flatline hemodynamics (0/0 pressures, `flags.arrestActive`), only the rhythm/ECG differs. V-Fib's outcome patch deliberately does NOT set `hr` (a fibrillatory rhythm has no organized rate - fabricating one would be less accurate than leaving it, and IntelliVue's own native engine already shows `--` for HR during vfib regardless); V-Tach's sets `hr:180` as a representative fast monomorphic rate. **HemoSphere Alta has zero rhythm-dependent rendering at all** (confirmed via grep - no `rhythm` references anywhere in that file, its waveform/PR tile are driven purely by HR/pulse-rate numbers) so none of this needed any HemoSphere changes; its PR tile will keep showing a rate number even during vfib, same pre-existing simplification the PEA outcome already had (see the "known, deliberate display simplifications" bullet).
- **Why the light/full split matters**: both devices' `layout()`-equivalent function resizes/clears the canvas (`canvas.width = ...` always clears, even to the same value) as a side effect. Calling it on every animation-frame tick during a 5-minute ramp would blank the scrolling waveform 60 times a second. Only call the full apply path on discrete navigation events, never from the ramp-ticking loop.
- **`tickNow(ts)` exists because of a real testing-environment gotcha**: the Browser pane's automated tab reports `document.hidden === true`, which fully suspends `requestAnimationFrame` (a real Chrome power-saving behavior, not a bug) - so the live tick loop provably never fires during automated verification. `tickNow` lets you manually drive one tick at an explicit timestamp to test the wiring without relying on rAF. This does not affect real users with a normal foreground tab.
- **Known, deliberate display simplifications** (not bugs - see README.md for the full explanation): neither device force-displays the engine's authored `ci`/`svr`/`svri`; both always compute those live from CO/height/weight or MAP/CVP/CO, matching real device behavior. IntelliVue has no literal "PEA" rhythm morphology - `PEA` maps to `sinus_tach` with the pulselessness conveyed by flat 0/0 arterial pressure.
- **`sync/deviceSync.js` closely mirrors the pacemaker's own SYNC_*/relay.* pattern on purpose** (interval-snapshot push + win-id self-echo guard + unconditional heartbeat + backoff-reconnect) rather than being designed from scratch - per the "do not introduce a second transport" architecture decision, any future third device (the pacemaker in Phase 5, an iPad peer) should use THIS module, not a fourth reimplementation.
- **The sync payload never includes `activeRamp`** - only `{partIndex, stepIndex, state}`. `activeRamp.startedAtMs` is a `performance.now()` timestamp with a clock origin local to one page load; syncing it across windows (different clock origins even same-machine) or devices (completely different machines over the relay) would be meaningless. Instead, whichever device is actively driving a ramp ticks it locally (Phase 2's `flagshipTick`) and the interval push broadcasts each already-interpolated `state` snapshot; a receiving device's `onRemoteSnapshot` always clears its own `activeRamp` to `null` and just displays incoming numbers - it never runs independent ramp math for a scenario a peer is driving. If you add a new kind of time-relative field to the engine, do NOT put it in the sync snapshot without solving this same problem first.
- **`onRemoteSnapshot` distinguishes a "full" apply (calls `renderFlagshipUI()`, refreshes tile visibility) from a "light" apply (`applyEngineValuesLight()` only)** by comparing the incoming `partIndex`/`stepIndex` against the runner's current values before overwriting them - i.e. it detects discrete navigation vs. an in-progress ramp's numbers changing, mirroring the exact same full/light distinction Phase 2 established for locally-driven ticks. Don't always full-apply on every remote message; the whole reason for the light path (avoiding a `layout()` call) applies equally to remote-driven updates.
- **Testing environment gotcha, same root cause as `tickNow()`**: `setInterval` (not just `requestAnimationFrame`) is aggressively throttled on the Browser pane's always-hidden automated tab - the 140ms push interval effectively never fires there. `deviceSync`'s returned object exposes `pushNow()` (bypasses the interval, still deduped against unchanged state) and `heartbeatNow()` (unconditional resend, bypasses dedupe too) for exactly this reason; both device files expose them via `window.ctSharedEngine.syncPushNow`/`syncHeartbeatNow`/`syncSetRelay`. None of this affects real users on a normal foreground tab, where the interval runs fine.
- **The relay path was verified with a plain Node `WebSocket` client joining the same room** (zero access to the browser's BroadcastChannel/localStorage), not just by observing two same-machine tabs update each other - that would have been ambiguous about which transport actually delivered the message, since all three fire unconditionally on every send. If you touch the relay protocol, re-verify the same way rather than trusting same-machine tab behavior alone.
- **Pacer bridge mechanics (Phase 5)**: `window.__pacerBridge.getState()`'s `captured` field is a *faithful reuse* of the exact boolean expression `computeAnnunConditions()` already uses for its own "LOSS OF V CAPTURE" condition (`f.pV && S.vOut>0 && vLeadOk() && P.batt!=='depleted' && S.vOut>=P.vThr`, plus `S.power`/self-test/`!S.paused` gates that function's early-return handles differently and a bridge consumer can't rely on the same way) - phrased as the positive case. If the pacemaker's own capture logic ever changes, update `pacerCapturedNow()` to match or the two will drift apart silently.
- **Two connection steps are required before the pacemaker can ever show `captured: true`, both realistic, neither a bug**: (1) `S.power` must be on (obviously), past the ~1.5s self-test (`S.selfTestUntil`); (2) `conn.vGen` (the V lead's *generator-end* plug, toggled by the `f-discV` checkbox / the Connections modal) defaults to `false` - a freshly-loaded pacemaker is not physically "plugged in" yet, matching real device setup. Don't mistake either gate for a wiring bug when testing.
- **`window.__pacerBridge.__testAdvanceClock(steps)` exists for the same reason as `tickNow()`/`pushNow()`**: the pacemaker's own internal clock `T` only advances via its `requestAnimationFrame` loop (`loop()` -> `step()`), which this environment's always-hidden automated tab fully suspends - so the ~1.5s self-test gate never clears without it. It calls the real `step()` function N times (literally the same state-machine advance `loop()` would have called via N real frames), not a shortcut around any gate. Does not affect real users on a normal foreground tab.
- **The pacemaker's own sync (`SYNC_KEY`/`BroadcastChannel('sim5392')`/`relay.*`, all defined near the top of its script) and the new Phase 5 bridge (`sync/deviceSync.js`, in the separate `<script type="module">` tag at the very end) are two fully independent systems that happen to run in the same page - and, importantly, BOTH read the identical `?relay=`/`?code=` URL params.** This is a real collision, not a hypothetical: opening a console-generated pacemaker link (`?role=learner&relay=X&code=Y`) makes BOTH systems connect to the SAME relay room at once, so each receives the other's differently-shaped messages over that room (the pacemaker's own `{win,data}` format vs. the bridge's `{partIndex,stepIndex,state,mode}` format). The pacemaker's own `applyRemote` already happens to no-op safely on the bridge's shape (no `.s` property), but that was luck, not a guarantee - so `sync/deviceSync.js` exports `isValidSnapshot()` and every one of this project's four `onRemoteSnapshot` implementations (console, IntelliVue, HemoSphere, this bridge) calls it before touching the payload. If you add a fifth consumer or change the snapshot shape, keep this guard.

## Platform generalization — Clinical Patient Simulator (post-CT-surgery-specific work)

**2026-08-23: a full repository audit + 10-phase implementation plan was written and approved** for evolving this repo from a single CT-surgery scenario into a general, extensible Clinical Patient Simulator (multiple populations, a Scenario Builder, real pharmacology, a pulsatility/CPR/mechanical-support model, Supabase-backed cross-device sessions, and a shared Swiss-grid design system for facilitator-facing surfaces only — the three learner-facing device shells keep their own realistic chrome unchanged). The full audit (architecture, gaps, proposed schema v2, precedence hierarchy, phase-by-phase detail, risks) is preserved as a published artifact; ask the user for the link if you need to re-read it rather than re-deriving any of this from scratch.

**Decisions made when the audit was approved** (do not re-litigate without asking):
- **Roles**: *Facilitator* = run a session, adjust any published scenario live, connect devices — no login required, matches how the console already works today. *Author* = build/save scenarios in the Scenario Builder — requires passcode-style protection, layered on once Supabase Auth exists (Phase 3 foundation → enforced in Phase 4). These are two different roles, not tiers of the same one.
- **Per-device local scenario panels stay** (IntelliVue's/HemoSphere's own "Shared Flagship Scenario" mini-drivers) — explicitly re-confirmed, not just carried over by default: the user wants every monitor independently usable solo, console or no console. Same precedent as the original Phase 4 "important product decision" above; this makes it doubly explicit for the Scenario Builder/registry work in Phase 4 of the new plan — don't strip these when scenarios move to a registry.
- **Population scope v1**: broadly "all RNs, inpatient" — not narrowly ICU/CT-surgery-only. Schema v2 (population field, staged/branching model) should stay genuinely population-agnostic rather than quietly CT-surgery-shaped; CT surgery is the first authored population, not the only one the schema assumes.
- **Real-time platform: Supabase**, free tier confirmed sufficient, **Supabase Auth magic-link** confirmed sufficient for facilitator/author login. No SSO requirement.
- **Supabase readiness**: a real project now exists and the foundation is built - see "Supabase foundation is built and live" below. Still no CLI/MCP connector available in this dev environment (re-confirmed on 2026-08-23) - `supabase/schema.sql` is applied by hand via the dashboard's SQL Editor, not a CLI-managed migration. If a CLI/MCP connector becomes available later, that file's contents are exactly what the first real migration should contain.

**Phase 2 (shared design system, homepage, navigation) is done.**
- New `design-system/` directory: `tokens.css` (color/type/spacing/radius/12-col-grid tokens — Archivo display + IBM Plex Sans body + IBM Plex Mono data/tabular, dark by default matching every other page in this product), `components.css` (page-head, numbered setup-steps, launch-card grid, section-label, pill, doc-foot — reusable across every future admin/facilitator surface), `presence.js` (+ 5 passing tests). Scoped explicitly to non-device surfaces only — never import into IntelliVue/HemoSphere/the pacemaker's own chrome.
